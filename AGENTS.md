# AGENTS.md — Keenetic Knowledge Base, lean agent contract

**Read on every task; do not preload the full archive or documentation tree.** This repository is a research notebook, provenance archive and knowledge workshop, **not** the production source of truth for Keenetic Auto Setup, link-generators, web4core, Entware, VPS gateway, NVR or other independent projects. Check the current tree and exact commit SHA before editing. Longer original agent instructions are preserved in the task-scoped guides below.

## Mission and trust boundaries

- Process knowledge as **raw source → inventory/classification → independent verification → concise topic article → optional promotion to the actual owning repository**, keeping original provenance or a carefully documented archive. Preserve useful historical context and negative results. Do not confuse a catalog entry with verified guidance.
- Classify every substantive claim as **Observed** (actual field observation, with limits), **Confirmed** (checked against current authoritative code/docs), **Historical** (previous version or setup), or **Hypothesis / Research** (not yet verified). An AI answer, quoted Telegram claim or plausible mechanism is never automatically Confirmed. Do not invent test results, device support, version claims or citations.
- **Code in the owning project takes precedence.** A recipe relating to KAS, link-generators/web4core, Entware, Mihomo or the VPS projects must be checked in that actual repository before being described as supported behavior. Reuse this repo's records as evidence, not as permission or competing configuration authority.
- **Protect the owner's original material.** A file's age, awkward format, duplicated fragments or conversation style does not justify deletion or sweeping rewrites. Inventory and classify first; preserve unique links, diagnostics, observed failures, exact commands and reasons for decisions. Prefer **extract + preserve** over rewrite-in-place. `archive/` and `archive/raw/` contain provenance, not instructions to execute.
- **TechnoBypass/Telegram is a source corpus, not a technical authority.** For imports preserve relevant message IDs, dates, source URLs and forwarded attribution; deduplicate conservatively without collapsing distinct messages/releases/issues. Imported entries begin as Source/Research. **Never commit raw Telegram HTML exports by default** or private-channel information, access tokens, credentials, private keys, secret-bearing subscription URLs or private infrastructure details.
- **Publications and licensing are scoped.** `tools/prepare_site_docs.py` stages only the maintained explicit MkDocs allowlist. Do not accidentally add raw/archive/catalog files or agent guides to published pages. `COPYRIGHT_AND_LICENSING.md` licenses only its explicitly listed works (20 curated CC BY articles and specified MIT code); do not silently apply those licenses to archival, third-party or new files. Preserve third-party attribution and provenance.
- Scripts and copied commands can affect routers, VPS, firewall, policy routing, DNS, VPN or persistent state. **No live execution or mutation** without explicit, task-specific **owner GO**, access/recovery checks and safe rollback. Do not present untested chat commands as verified; reject unsafe examples such as blind `curl | sh`, global firewall flush, `eval`, `chmod 777` or disabled TLS checks unless accurately documented as risks.
- Owner's [shared task contract](https://github.com/saymer-alt/saymer-alt/blob/main/AGENT-TASK-CONTRACT.md) requires preserving intent, scope/non-goals, protected assets, approvals, negative verification and Definition of Done for substantial tasks. For large new subsystems use [Proof Before Build](https://github.com/saymer-alt/saymer-alt/blob/main/PROOF-BEFORE-BUILD.md): assess no change, smallest safe solution, evidence, ongoing cost and STOP criteria. No broad refactoring for style alone.

## Practical, bounded workflow

1. Verify repository, branch, base SHA, task, source provenance and relevant existing documents. Identify whether the work is archiving, research, editorial, scripting or cross-project implementation.
2. **Load only the relevant guide** linked below. Check the primary source, current code or upstream documentation for current claims; leave UNKNOWN/Research labels where validation cannot be demonstrated.
3. Prefer a minimal topic-scoped diff. Preserve original raw material and evidence; never mass-move, delete or rename without an inventory/mapping, repaired links and explicit owner scope. Keep `README.md` truthful about the files that *actually* exist. Maintained articles normally use Russian and identify prerequisites, verification and recovery where applicable.
4. Review the exact diff for truncation, broken links, accidental license/scope changes, secret exposure and safety regressions. Check relevant offline/site tests. Do not edit live systems, deploy GitHub Pages, merge into `main`, rewrite history, force-push or promote changes to another repo without separate authorization. Work in a task branch / **Draft PR**.
5. Report the final commit SHA and evidence precisely as **PASS / FAIL / BLOCKED / NOT TESTED**. Mark archival evidence Historical, not current; record unverified claims explicitly.
