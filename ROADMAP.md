# ROADMAP — Keenetic Knowledge Base

Этот план описывает не разработку одной программы, а переработку накопленного технического
архива в поддерживаемую базу знаний и источник полезных материалов для других проектов.

Главный принцип: **сначала понять и сохранить, потом переносить и чистить**.

## Phase 0 — Working rules and truthful entry point

- [x] Добавить проектный `AGENTS.md`.
- [x] Зафиксировать назначение репозитория как knowledge workshop / research archive.
- [x] Убрать из README обещания несуществующих разделов.
- [x] Создать первичную инвентаризацию текущего дерева.
- [x] Зафиксировать этот roadmap.

Результат: новый агент может понять, что находится в репозитории, не принимая любой старый
файл за актуальную документацию.

## Phase 1 — Content audit

Для каждого существующего файла определить:

- реальную тему, а не тему по имени каталога;
- происхождение: реальный тест, рабочий скрипт, исследование, диалог, AI-ответ, творческий текст;
- наличие уникальных команд, наблюдений, failure cases и ссылок;
- актуальность;
- риск наличия секретов или приватной инфраструктурной информации;
- возможный канонический проект-владелец.

Классы из `AGENTS.md`:

- canonical;
- candidate;
- source/raw;
- project artifact;
- historical;
- unrelated;
- duplicate/obsolete.

`INVENTORY.md` — живой результат этого этапа. Статус файла можно повышать только после
проверки содержимого.


## Phase 2 — TechnoBypass source catalog

TechnoBypass становится постоянным входящим research source для этой базы.

Цель этапа — превратить Telegram-экспорты в пригодный для поиска слой навигации, не
объявляя содержимое канала автоматически проверенной документацией.

План:

- [x] извлечь message ID, дату, текстовый контекст, ссылки и forwarded provenance (TASK-TB-01)
- [x] сделать консервативную дедупликацию ссылок и проектов (TASK-TB-01/02A)
- [x] выделить реальные тематические группы по содержимому канала (TASK-TB-01)
- [x] создать Markdown-навигацию по темам (TASK-TB-01)
- [x] создать отдельный индекс GitHub/GitLab/других программных проектов (TASK-TB-01)
- [x] сохранить непонятные ресурсы в unclassified, а не потерять их (TASK-TB-01)
- [x] не коммитить raw HTML без отдельной необходимости (соблюдено)
- [x] проверить генерируемый каталог на секреты и приватные ссылки (TASK-TB-03)
- [x] определить high-value материалы для последующей технической проверки (TASK-TB-04)
- [x] определить кандидатов на promotion в активные проекты владельца (TASK-TB-06, PROMOTION_BACKLOG.md).

Предпочтительный логический поток:

```text
TechnoBypass
    ↓
source catalog
    ↓
topic/project indexes
    ↓
review
    ↓
Observed / Confirmed knowledge
    ↓
article or promotion into owning project
```

На этом этапе **не требуется проверять каждую внешнюю ссылку в интернете**. Сначала нужен
полезный индекс всего накопленного материала; массовая verification campaign — отдельная
задача.

Raw Telegram export остаётся входным материалом. В публичный GitHub должен попадать
нормализованный результат: темы, проекты, ссылки, описания, статусы и provenance.

## Phase 3 — Preserve before moving

До массовой реорганизации:

- определить, какие сырые материалы должны остаться доступными как provenance;
- выбрать структуру архива, например `archive/raw/` и `archive/historical/`;
- проверить внутренние ссылки;
- не смешивать перемещение файлов с их содержательной переписью;
- крупные файлы разбирать по темам до удаления или замены исходника.

Особое внимание:

- `moshub.md` — очень крупный исследовательский файл;
- `proxy.md` — знание извлечено 2026-09-24 (см. Phase 4); будущее перемещение файла в архив — отдельное решение владельца;
- `NVR/WL.md` — пример файла, лежащего не в своей тематической области;
- MosTech/VirtIO-FS материалы — отделить полезные технические наблюдения от творческого текста.

## Phase 5 — Promote useful results into active projects

Если найденный материал относится к уже существующему проекту:

1. прочитать его `AGENTS.md`;
2. проверить текущую реализацию;
3. найти расхождения со старым материалом;
4. перенести только подтверждённую часть;
5. выполнить тесты/проверки самого целевого проекта;
6. оставить здесь ссылку или краткое объяснение происхождения, если это полезно.

Предполагаемые направления:

| Тема | Вероятный проект-владелец |
|---|---|
| Keenetic + Mihomo install/watchdog | `keenetic-auto-setup` |
| Генерация Mihomo/WG/AWG конфигураций | `link-generators` / web4core fork |
| Entware package build/feed | `entware-go` |
| VPS AmneziaWG → Mihomo routing | VPS gateway/bootstrap project |
| Общие концепции и исследовательские заметки | этот репозиторий |

Никакой автоматической синхронизации копипастой между репозиториями.

## Phase 6 — Build the real knowledge-base structure

Только после аудита выбрать окончательное дерево.

Возможный вариант, не обязательный контракт:

```text
docs/
  keenetic/
  entware/
  networking/
  vpn/
  proxy/
  mihomo/
  dpi/
  nvr/
reference/
scripts/
archive/
  raw/
  historical/
```

Требования:

- README ссылается только на реально существующие разделы;
- один материал — один понятный владелец/назначение;
- raw и canonical явно различимы;
- отсутствуют фиктивные разделы и пустые каталоги «на будущее».

## Phase 7 — Maintenance model

После основной переработки:

- новые TechnoBypass-экспорты периодически импортируются в source catalog с дедупликацией;
- уже вручную проверенные описания/статусы не должны бездумно перезаписываться повторным импортом;
- новые исследования сначала попадают как source/raw;
- канонический статус требует проверки;
- при изменении внешнего проекта проверяется, не устарела ли соответствующая статья;
- периодически просматриваются крупные raw-файлы на предмет новых кандидатов;
- не копится новый «безымянный» мусор в корне.

## Definition of done

Репозиторий можно считать настоящей knowledge base, когда:

- README соответствует реальному дереву;
- TechnoBypass имеет поддерживаемый searchable catalog с provenance до исходных сообщений;
- повторные ссылки не превращают каталог в дубликаты;
- каждый заметный файл имеет понятный статус и назначение;
- сырые AI/chat материалы не выглядят как проверенная инструкция;
- критичные команды имеют контекст и recovery path;
- активные проекты не дублируются здесь как альтернативные источники истины;
- полезные находки из старого архива либо оформлены здесь, либо перенесены в проект-владелец;
- старые материалы сохранены настолько, насколько они нужны для provenance и истории решений.
