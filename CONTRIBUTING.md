# Участие в проекте / Contributing

Предложения, исправления опечаток, проверенные технические замечания и небольшие Pull Requests приветствуются.

## Перед созданием Issue или PR

1. Прочитайте [README](README.md) и документацию проекта.
2. Проверьте существующие Issues и PR на дубли.
3. Для ошибок используйте форму Bug report; для улучшений — Feature request.
4. Работайте в отдельной ветке от актуального `main`; присылайте минимальный diff и объясняйте проверку.

## Особенности проекта

- Прочитайте `AGENTS.md`, `SOURCES.md` и `catalog/techno-bypass/README.md` до подачи материалов.
- Сохраняйте происхождение источника, ссылку и дату проверки; явно помечайте `Research`/`Observed`/`Confirmed` только на основании доказательств.
- Не превращайте старые чаты, ИИ-ответы или пересылки Telegram в проверенные инструкции без независимой верификации.
- Не отправляйте в публичный репозиторий приватные Telegram-экспорты, чужие полные статьи, токены и закрытые конфигурации.
- Не назначайте общую лицензию на материалы без проверки `SOURCES.md` и происхождения контента.

## Лицензирование новых изменений

- Прочитайте [области MIT и CC BY 4.0](COPYRIGHT_AND_LICENSING.md): новые лицензии относятся только к явно перечисленным авторским материалам.
- Предлагая собственный текст в уже лицензируемой статье, убедитесь, что можете разрешить его использование по **CC BY 4.0**, с указанием авторства. Собственный код в перечисленных инструментах — по **MIT**.
- Не присылайте текст/скрипты из чужого проекта без совместимых разрешений и сохранения уведомлений. Если права или происхождение неясны, приложите ссылку и предложите сначала provenance-review.
- Новые файлы, `archive/`, `MosTech/`, `catalog/` и `NVR/` **не лицензируются автоматически**. Включение нового файла в перечень — отдельное изменение с явным решением владельца.

## Проверки и описание изменений

- Опишите наблюдаемое и ожидаемое поведение, точные версии и ограничения.
- Приведите минимальный пример или ссылку на источник; удалите из логов и примеров закрытые данные.
- Запустите применимые проверки из `tests/` и CI, либо явно укажите, что не удалось проверить.
- Не заявляйте тестирование на физическом оборудовании/production VPS, если теста не было.
- Не изменяйте теги релизов или `stable` в обычном PR к документации.

## Конфиденциальность

Нераскрытые уязвимости и секреты **не** публикуйте через публичные Issues/PR. Приватный канал раскрытия уязвимостей должен быть настроен и проверен отдельно. Публичные Issues предназначены только для несекретных ошибок.
