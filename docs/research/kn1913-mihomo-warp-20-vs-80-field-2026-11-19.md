# Полевой тест KN-1913: 80 → 20 Cloudflare WARP/AWG в Mihomo (19.11.2026)

**Статус:** Observed / field evidence, не универсальный бенчмарк  
**Устройство:** Keenetic Viva KN-1913, слабый по ресурсам MIPSel-роутер (со слов владельца)  
**Дата:** 2026-11-19, несколько последовательных тестов в одном сетевом окружении  
**Источники:** переписка владельца с приложенными скриншотами MetaCubeXD от 19.11.2026 и локально разобранные YAML v1–v6 (сырые конфиги, HWID, ключи и секретные ссылки **не публикуются**)  
**Назначение:** сохранить практическую матрицу результатов, отрицательные примеры и правила для будущих подборок Mihomo/Link Generators/KAS.

## Краткий результат

**Observed (владелец):** первоначальный набор из 80 прямых Cloudflare WARP/AWG WireGuard-прокси с двумя HTTP-подписками ощущался слишком тяжёлым для KN-1913. После сокращения до 20 WG и нескольких итераций замены адресов владелец сообщил, что в **v6 все 20 WG заработали**, причём **не сразу**. На финальном скриншоте видны **16 WG с ответами 72–98 мс**; ещё четыре WG не попали в видимую область кадра и известны как рабочие **только по сообщению владельца**. Эти числа — задержки проверки MetaCubeXD, а не результаты нагрузочного теста или измерения пропускной способности.

**Hypothesis:** значительная часть нестабильности при 80 узлах могла происходить из-за затрат на параллельные/частые health-check и/или нагрузки на CPU/память роутера, а не из-за отсутствия маршрута у всех неподтвердившихся адресов. **Не подтверждено измерениями:** нет логов Mihomo, замеров RSS/CPU/zRAM, профиля конкуренции тестов и сравнимого статистического A/B-теста на 80 и 20 прокси. Следовательно, «на KN-1913 80 не работает» нельзя делать универсальным техническим пределом.

Параметры 300/600 с — настройки периодического опроса, а не измеренное время завершения одного теста. Сохранение провайдеров и их HWID **не подтверждает** доступность каждого узла внутри подписки: в части скриншотов у провайдерских VLESS/HY2 было «---»/индикатор проверки.

## Итерации и отрицательные результаты

1. **80 + две подписки:** пользователем отмечена тяжёлая работа роутера; точных измерений нагрузки нет.
2. **Первая сокращённая версия, 20 + 2:** при первоначальном тестировании у FRA-004, FRA-008, FRA-011, FRA-020, FRA-062 отсутствовало успешное значение задержки («---»). Тогда их заменили. Это **одноразовый провал проверки, не доказанный устойчивый отказ**. FRA-007 и FRA-015 позднее временно выглядели «зависшими», но владелец объяснил, что неоднократно запускал тест вручную: считать их однозначно нерабочими было ошибкой.
3. **v2:** вместо исходных пяти добавлены FRA-014, FRA-010, FRA-024, FRA-058 и FRA-001. Большинство результатов составляли примерно 85–109 мс; отдельные ответы были 347–408 мс. FRA-014 позднее показывал 86 мс после 347 мс — единичный высокий ping **не** достаточен для отбраковки.
4. **v3:** FRA-007 → FRA-018, FRA-015 → FRA-026. На последующих замерах FRA-026 завершил проверку без ответа, FRA-058 отвечал медленно (348 мс), FRA-006 — 192 мс. Владелец также наблюдал быстрые ответы 84–121 мс у других WG.
5. **v4:** FRA-026 → FRA-044, FRA-058 → FRA-078. Интервал проверок групп/провайдеров поднят до 600 с. На полном дополнительном скриншоте без успешной задержки были **три**, а не два, узла: FRA-012, FRA-019, FRA-035. Первый раз при просмотре пропустили FRA-035; это отдельный урок по качеству визуальной инвентаризации.
6. **v5:** FRA-012 → FRA-023, FRA-019 → FRA-045. По скриншоту видны быстрые ответы 80–103 мс, включая FRA-045; FRA-035 всё ещё не дал подтверждённого результата.
7. **v6:** FRA-035 → FRA-021. Владелец сообщил: **все 20 WG заработали, но не сразу**. На видимой части финального скриншота 16 WG с задержкой 72–98 мс; стабилизация, распределение причин и длительная надёжность не измерялись.

Ни один из шагов выше **не является** доказательством успешного туннельного обмена каждым вариантом в течение суток: это выборочные проверки задержки/доступности через UI.

## Практические правила для следующих испытаний

- Для слабых моделей **начинать с умеренного пула, например 10–20 WG**, и увеличивать только при наличии ресурсов. Число 20 — успешный **полевой пример** для конкретного KN-1913, а не объявленный платформенный лимит.
- Не считать «---»/крутящийся индикатор доказательством окончательно мёртвого endpoint. Разделять: pending → timeout/no result → успешная задержка → подтверждённый обмен полезным трафиком.
- Не нажимать кнопку массового теста многократно; дождаться окончания первого прохода, повторить позже и сравнить 2–3 независимых замера. Отдельно проверять живость через реальные запросы.
- Не заменять рабочие WG только из-за единичного роста RTT (полевой пример: FRA-014 347 → 86 мс, позднее 84–98 мс).
- На слабом устройстве рассматривать разрежение интервала проверок (в успешном файле 600 с вместо 300 с) и ограничение одновременно тестируемых узлов **как гипотезы для нагрузочного измерения**, а не как доказанный фикс.
- При переборе сохранять рабочую часть пула, менять только недоказавшие доступность адреса. Хранить матрицу ID, IP/UDP (в защищённой среде), результат/дата/сеть, номер версии, RTT, фактический тест трафика.
- Проверять итоговый YAML: ровно 20 WG, отсутствие «висячих» имён в proxy-groups, неизменность двух providers/HWID, отсутствие случайного DIRECT и IPv6.
- Иметь резервный конфиг и доступ к локальному управлению для отката. Не загружать в публичный репозиторий приватные WG-ключи, I1–I5/обфускационные поля, секретные подписки, HWID или полный YAML.

## Что измерить в следующем A/B тесте

1. При одинаковых сети/устройстве/времени сравнить профили 10 / 20 / 40 / 80 WG: RSS Mihomo, память system/zRAM, load/CPU, uptime, падения/restart, UI responsiveness.
2. Указать фактическое число нод в двух providers: вклад providers нельзя считать нулевым только потому, что в YAML 20 прямых WG.
3. Сравнить длительность одиночной групповой проверки, p50/p95 RTT и процент таймаутов, затем повторить реальным HTTP(S) запросом через каждый WG.
4. Проверить влияние interval 300 vs 600 при равном числе nodes; отдельно повторить без ручного спама кнопки тестирования.
5. Разнести объяснения отказов: роутер перегружен, rate limiting проверочного URL, UDP endpoint недоступен, короткий timeout, поведение Anycast, у подписки ошибка. Пока для каждого из них нет отличающих измерений.

## Идеи для других проектов (backlog only)

**Link Generators / Universal Mihomo Builder:** опциональный профиль «ресурсно ограниченный роутер», лимит N прямых WG (ориентир 10/20, редактируемо), сохранение всех провайдеров/HWID, приоритизация уже проверенных узлов, выдача списка исключений и объяснения про health-check. Не реализовывать автоматически и не ухудшать мощные устройства.

**KAS / Mihomo:** документировать диагностику массовой проверки и интервалов, не менять настройки живого устройства без согласования. Продуктовая поддержка — предмет отдельной задачи и тестов.

## Границы доказательств и сохранность

- **Observed:** полевые скриншоты владельца KN-1913 19.11.2026; финальное заявление владельца о работоспособности всех 20 WG.
- **Confirmed локальной статической проверкой:** количество прямых прокси, имена, интервалы, группы, два providers и параметры из YAML; это **не** runtime proof.
- **Hypothesis:** снижение нагрузки при уменьшении 80→20 именно из-за объёма/частоты тестов; возможно участие DPI/Anycast и сетевых колебаний.
- **Not tested:** длительная стабильность, throughput, загрузка CPU/RAM, конкретные причины первоначальных «---», активная работоспособность всех узлов подписок.
- **Безопасность:** сырые конфиги и скриншоты остаются вне публичного репозитория; в этой записи только безсекретные идентификаторы, результаты и методика.
